# End-to-end test against a real MySQL (2026-09-28)

First end-to-end run against a **real** database reachable only over SSH — not the unit-test fakes.
Nothing here is a claim about other deployments; it is one machine, one schema, one account.

## Setup

- Server: a test box (4 vCPU / 8 GB) running a containerised MySQL 8.0.36 whose 3306 is published on
  the host; the SSH host is reachable on port 22.
- Account: a dedicated `mcp_ro` user, granted **`SELECT` on two schemas only**. The administrative
  password never left the server and the application password exists only in the untracked `.env`
  (`.gitignore` covers `.env`).
- Client: this repository's `server.py`, launched over stdio by a small MCP client, with
  `MCP_SSH_HOST` / `MCP_SSH_PEM` / `MCP_DB_*` pointed at that server and `MCP_ENABLE_MUTATING_TOOLS=0`.

## Results

| # | what was attempted | expected | observed |
|---|---|---|---|
| 1 | list tools | 17 read-only tools, no mutating ones | **17 tools; `docker_restart` / `deploy_backend_jar` / `deploy_frontend` absent** |
| 2 | read `information_schema.tables` for the schema over the tunnel | rows | **returned the five tables of that schema** |
| 3 | `SELECT 1` | rows | returned `[{"ok": 1}]` |
| 4 | `UPDATE ... SET ...` | refused by the guard | `ERROR: only read-only statements are allowed (select/with/show/describe/explain)` |
| 5 | `SELECT 1; DROP TABLE ...` | refused | `ERROR: multiple statements are not allowed` |
| 6 | `SELECT 1 INTO OUTFILE ...` | refused | `ERROR: forbidden keyword: OUTFILE` |
| 7 | `SELECT 1 INTO/**/OUTFILE ...` (keyword split by a comment) | refused | `ERROR: forbidden keyword: OUTFILE` — the guard normalises comments before the keyword check |
| 8 | `SELECT 1 INTO OUT/**/FILE ...` (split mid-keyword) | refused | **passed the guard**, then MySQL rejected it with a syntax error (1064) |
| 9 | the same account issuing `CREATE TABLE` directly | denied by the database | `ERROR 1142: CREATE command denied` |
| 10 | the example domain tool `list_activities` | depends on the schema | `Table '...lottery_activity' doesn't exist` — expected: the eight domain tools are examples for the campaign schema in the README |

## What this does and does not show

- **It shows** that the transport path works against a real host (paramiko public-key auth plus the
  local port forward), that the default tool surface really is read-only, that the documented guard
  refuses the write shapes it claims to refuse, and that the **database grants are the primary
  control**: row 9 is the reason the README says the SQL guard is a backstop.
- **Row 8 is a detection gap, not a bypass.** The guard's comment handling can turn `OUT/**/FILE`
  into `OUT FILE`, which does not match the forbidden keyword; MySQL then refuses the statement
  itself. It is worth stating plainly because it shows the guard's normalisation is a heuristic:
  the authoritative control is the account's privileges, and the guard's job is to make the common
  mistakes fail loudly rather than to be a parser.
- **It does not show** anything about other schemas, other MySQL versions, TLS, or the mutating ops
  tools (they were deliberately left unregistered).
- The eight example domain tools are schema-specific by design; point them at your own schema or
  delete them.

## Reproduce

```bash
# 1. a read-only account on a host reachable over SSH
# 2. an untracked .env with MCP_SSH_* / MCP_DB_* / MCP_ENABLE_MUTATING_TOOLS=0
# 3. an MCP client that calls tools; the probe used here is one page of stdio JSON-RPC
python server.py      # speaks MCP over stdio
```
